# 마법의 소라고동 구현 계획

상태: 검토용 초안. 사용자에게 확정받은 요구와 아래 기술 제안을 구분한다. 이 문서는 구현·배포 승인이나 검증 완료 기록이 아니다.

## 1. 목표와 확정 요구

- 학교 재학생과 승인 완료 선생님이 DataGSM으로 로그인하고 질문을 입력한다. 졸업생·자퇴생은 제외한다.
- 로그인은 고정 1시간 세션이며 만료 시 DataGSM으로 다시 로그인한다.
- 소라고동의 줄을 당기면 Jeb의 choice API가 정해진 대사 하나를 선택한다.
- 첫 버전은 줄 당기기 애니메이션과 텍스트 답변까지 제공한다. 음성은 제외한다.
- Vercel 등 서버리스 환경에 배포한다.
- 관리형 Redis 호환 공유 저장소를 사용한다. 공급자·요금제·연결 클라이언트는 별도 선정한다.
- 소라고동은 첨부한 참고 이미지의 형태를 기준으로 Three.js에서 직접 제작한 3D 모델로 구현한다. 완성 모델 다운로드나 평면 이미지를 3D인 것처럼 표시하는 방식은 사용하지 않는다.
- 현재 Next.js 16 App Router 단일 앱과 FSD 경계를 유지한다.
- 이번 작업은 계획 수립이다. 코드 구현, 의존성 설치, 외부 서비스 생성, 커밋·푸시·배포는 별도 요청 이후 진행한다.

## 2. 관측 근거와 미확인 사항

### 관측한 사실

- 현재 저장소는 main 브랜치의 기본 템플릿이며 계획 작성 전 작업 트리가 깨끗했다.
- 실제 페이지는 src/app/page.tsx → views/home의 HomeView이고 도메인 기능·인증·제품 테스트는 아직 없다.
- package.json에는 React Hook Form, zod, shadcn, DataGSM SDK, Redis 클라이언트, Vitest, Playwright가 없다.
- next.config.ts는 API_BASE_URL을 요구하고 /backend rewrite를 제공한다. 해당 공개 계약은 보존한다.
- 사용자가 실제 Jeb 호출에서 200, 401 invalid_api_key, 422 missing·union_tag_invalid 응답을 확보했다. 이 호출은 사용자가 실행한 것이며 에이전트가 직접 실행한 것은 아니다.
- 성공 응답은 model, answers.conch_answer(type, probabilities, choice, confidence), usage로 구성된다. choice는 문자열 키다.
- DataGSM OAuth 문서 18개를 검토했다. 문서상 사용자 정보는 objectType, status, student, teacher를 구분하며 isStudent는 deprecated다.

### 아직 관측하지 않은 것

- 실제 DataGSM 로그인, 토큰 교환, 학생·선생님 사용자 조회와 만료 동작.
- Jeb의 다양한 한국어 질문 선택 품질, 응답 지연, 429·5xx 응답 본문.
- 배포 환경의 외부 통신, 쿠키, Redis 연결, 여러 인스턴스 간 제어.
- 공지에서 학생 대상이라고 소개된 Jeb 키를 선생님이 사용하는 학교 앱에도 공유할 수 있는지의 제공자 허용 범위. 선생님 포함 공개 전에 확인한다.

## 3. 범위와 보류 항목

### 첫 버전

- 로그인, 로그인 실패·이용 제한 안내, 서버 세션, 로그아웃.
- 질문 입력·검증, 포인터로 줄 당기기, 키보드·버튼 대체 실행.
- 단답형 결과, 새 질문, 로딩·오류·만료·혼잡 상태.
- 서버 측 Jeb 호출, 런타임 응답 검증, 요청 중복 방지와 이용 제한.
- 반응형·키보드 접근성·모션 감소, 최소 운영 로그와 검증.

### 제외

- 음성, 음성 입력, 대화형 채팅, 자유 텍스트 생성.
- 질문 이력 영구 저장, 관리자 대시보드, 회원가입·별도 비밀번호.
- 별도 Spring/Nest 서버, 관계형 DB, 불필요한 UI·폼 라이브러리.
- 에피소드 이미지·음성 추출. 소라고동은 Three.js에서 직접 모델링하고 WebGL 미지원 상황에만 자체 정적 표현을 사용한다.
- 첫 버전의 DataGSM Refresh Token 장기 보관·자동 갱신. 로그인 지속 요구가 생기면 후속 범위로 검토한다.

## 5. 인증과 신뢰 경계

### 서버 주도 PKCE

1. 로그인 시작 요청에서 암호학적 난수로 state·code_verifier와 로그인 거래 식별자를 생성한다.
2. 거래를 Redis에 짧은 TTL로 저장하고 브라우저에는 거래 식별자만 HttpOnly 쿠키로 전달한다.
3. 서버가 S256 code_challenge를 생성하고 등록된 고정 redirect URI로 DataGSM 인증 URL을 구성한다.
4. 서버 콜백에서 code·state와 브라우저 거래 쿠키를 검증하고 거래를 일회성으로 소비한다.
5. DataGSM의 토큰 엔드포인트에 JSON 요청을 보내고 서버에서 /userinfo를 조회한다.
6. 외부 응답을 런타임 검증하고 이용 자격을 확인한 뒤 새 앱 세션을 만든다.
7. 앱 세션 쿠키에는 예측 불가능한 opaque ID만 넣는다. 저장소에서는 ID 해시로 조회한다.
8. 사용한 인증 거래와 쿠키를 정리하고 허용된 앱 내부 경로로 이동한다.

DataGSM 비밀번호는 앱에서 받지 않는다. OAuth state와 verifier는 누락·불일치·만료·재사용을 거부한다. 임의 next URL·Host 헤더로 callback URI를 만들지 않고 설정된 APP_ORIGIN·등록 URI를 사용한다.

### 이용 자격

- 공통: status가 ACTIVE이고 서버가 검증한 사용자 응답이어야 한다.
- 학생: objectType이 STUDENT, student 존재, isLeaveSchool이 false, role이 GENERAL_STUDENT·STUDENT_COUNCIL·DORMITORY_MANAGER 중 하나인 경우 허용한다.
- 선생님: objectType이 TEACHER, teacher 존재, status가 ACTIVE인 경우 허용.
- PENDING, null 대상, 미지원 값, 졸업생·자퇴생은 기본 거부한다.
- 상위 role=USER/ADMIN만으로 학생·선생님을 판단하지 않는다. 이메일 접미사만으로도 허용하지 않는다.
- 클라이언트가 전달한 isStudent·이름·학번·사용자 ID를 인증 근거로 쓰지 않는다.

### 앱 세션과 보안

- 세션에는 사용자 ID, 표시 이름, 대상 종류, 최소 이용 자격 정보, 검증 시각과 고정 만료시각만 보관한다. 기숙사·성별·전체 프로필은 보관하지 않는다.
- DataGSM 토큰은 로그인 처리 중만 사용하고 첫 버전에서는 보관하지 않는다. 이후 Refresh Token이 필요한 요구가 생기면 저장 암호화·갱신 경쟁·폐기를 포함해 재설계한다.
- 세션은 1시간 고정 TTL, 활동에 따른 무기한 연장 없음. 자격 변경은 새 로그인 때 반영되므로 최대 세션 기간의 반영 지연을 명시한다. 즉시 반영이 필요하면 재조회·재검증을 추가한다.
- 로그아웃은 해당 Redis 세션을 삭제하고 쿠키를 만료시킨다. DataGSM 전체 계정 로그아웃과 혼동하지 않는다.
- 운영 쿠키는 HttpOnly·Secure·SameSite=Lax·Path=/를 적용한다. 개발 localhost는 별도 환경 설정을 둔다.
- POST 요청은 정확한 Origin 검증, 세션 검증, JSON Content-Type 제한 등 CSRF 방어를 적용한다. OAuth state 검증은 로그인 후 POST의 CSRF 방어를 대체하지 않는다.
- 인증·개인화 응답은 캐시하지 않는다. 저장소 장애 시 인증이나 제한을 우회하지 않고 안전하게 실패한다.

## 6. 앱 API 계약 — 신규 경로 제안

모든 경로는 신규 제안이며 기존에 구현된 API가 아니다. 공개 호출자는 신뢰하지 않는 브라우저다. 인증·이용 자격 확인은 매 요청 서버에서 수행한다.

| 경로               | 메서드 | 인증·동작                                          | 응답                                 |
| ------------------ | ------ | -------------------------------------------------- | ------------------------------------ |
| /api/auth/login    | GET    | 비로그인 허용, 요청 빈도 제한, 거래 생성·PKCE 시작 | DataGSM으로 redirect                 |
| /api/auth/callback | GET    | OAuth 거래·state·code 검증, 자격 검사·세션 발급    | / 또는 /login 오류 화면으로 redirect |
| /api/auth/session  | GET    | 서버 세션 검증, 최소 사용자 정보 조회              | JSON 성공·오류                       |
| /api/auth/logout   | POST   | Origin 검증, 있으면 세션 폐기. 반복 호출도 안전    | JSON 성공                            |
| /api/conch/answer  | POST   | Origin·세션·자격·입력·예산·동시성·중복 확인        | JSON 답변·오류                       |

### 동일한 JSON 형태

- 성공: data 필드에 해당 결과를 둔다. 세션 조회는 최소 사용자 정보, 질문 응답은 requestId·answerId·answerText를 반환한다.
- 실패: error 객체에 안정적인 code와 안전한 한국어 message를 둔다. 제한 안내에는 필요 시 retryAfterSeconds를 추가한다.
- 리다이렉트 경로는 JSON envelope 예외다. 로그인 실패는 허용 목록의 짧은 오류 코드로 전달하고 외부 원문 메시지·토큰은 URL에 넣지 않는다.
- Jeb probabilities·confidence·usage는 첫 화면의 공개 응답에 필요하지 않다. 개인정보 없는 진단값만 필요 시 서버에서 사용한다.
- 기존 /backend rewrite는 유지한다. 브라우저에서는 /api를 호출할 별도 동일 출처 API 클라이언트·메서드 래퍼를 shared/api에 추가하고 기존 get/post의 계약을 바꾸지 않는다.
- 신규 JSON API의 첫 소비자는 이 저장소 UI뿐이다. 기존 API 마이그레이션·폐기 대상 없음.

### 멱등성·중복

- 질문 요청은 question과 requestId를 받는다. requestId 형식과 입력을 서버에서 검증한다.
- 같은 사용자·requestId는 짧은 TTL의 동일 처리 결과를 반환하고 새 Jeb 호출을 만들지 않는다.
- 같은 ID에 다른 질문 해시가 오면 409로 거부한다. 진행 중이면 pending 충돌 상태를 반환한다.
- upstream 타임아웃은 처리 여부가 불명확할 수 있으므로 같은 ID를 즉시 재호출하지 않는다. 모호한 결과를 짧은 기간 보관하고 UI에서 새 시도 여부를 사용자가 결정하게 한다.
- 클라이언트 mutation과 서버에서 Jeb 호출의 자동 재시도를 하지 않는다. 전역 queries retry 설정과 별개로 mutation retry를 명시한다.
- 이전 요청 응답이 새 질문 상태를 덮어쓰지 않도록 요청 식별자를 비교한다.

### 오류 처리 계약

| 실패                             | 앱 상태·코드 제안              | 사용자 동작·로그 정책                                              |
| -------------------------------- | ------------------------------ | ------------------------------------------------------------------ |
| 잘못된 앱 입력                   | 400 / INVALID_QUESTION         | 입력 수정. 질문 원문 로그 금지                                     |
| 미로그인·만료                    | 401 / AUTH_REQUIRED            | 로그인 안내. 인증 쿠키·토큰 로그 금지                              |
| 이용 자격 없음·Origin 불일치     | 403 / ACCESS_DENIED            | 안전한 이용 제한 안내                                              |
| 중복 요청 진행 중·ID 재사용 충돌 | 409 / REQUEST_CONFLICT         | 자동 재호출 금지                                                   |
| 개인·공용 한도·동시 슬롯 부족    | 429 / RATE_LIMITED             | Retry-After 또는 다음 초기화 안내                                  |
| Jeb 401 invalid_api_key          | 503 / SERVICE_UNAVAILABLE      | 앱 로그인 오류로 취급하지 않음. 관리자 설정 문제 로그, 키는 비노출 |
| Jeb 422                          | 502 / UPSTREAM_INVALID_REQUEST | 서버 계약 문제. 이용자 입력 책임으로 돌리지 않음                   |
| Jeb 429                          | 429 / RATE_LIMITED             | 알려지지 않은 본문도 처리. bounded 안내                            |
| Jeb 5xx·예상하지 못한 JSON       | 502 / UPSTREAM_ERROR           | 수동 재시도 안내, 원문 응답 노출 금지                              |
| upstream 타임아웃                | 504 / UPSTREAM_TIMEOUT         | 결과 불명확 상태. 자동 재시도 금지                                 |
| Redis 장애                       | 503 / SERVICE_UNAVAILABLE      | fail closed, 일시 장애 안내                                        |
| 예외                             | 500 / INTERNAL_ERROR           | requestId와 정제된 오류 분류만 로그                                |

이 표의 앱 오류는 설계안이다. 미관측 upstream 오류를 실제 확인된 응답처럼 문서화하지 않는다.

## 7. Jeb 처리

- 외부 endpoint는 https://jeb.https.gsmsv.site/v1/systemone이며 서버 전용 Bearer 키로 호출한다.
- request state에는 질문과 필요한 오락용 문맥만 넣고 이름·학번·이메일·학생 정보를 넣지 않는다.
- questions.conch_answer에 choice, 캐릭터 지침, 고정 criteria를 설정한다.
- 답변 후보: 응 / 아니 / 어쩌면 언젠가는 / 다시 물어봐 / 아무것도 하지 마 / 둘 다 안 돼. 한국어 표현은 앱 대사이며 공식 더빙 인용으로 주장하지 않는다.
- 짧고 무심한 단답형, 이유 설명 없음, 현실 미래 예측이 아닌 오락용이라는 지침을 적용한다.
- 질문 안의 지시로 choice 목록·시스템 지침·키·모델을 바꾸지 않는다. 이 방식만으로 모든 의미적 prompt injection이 차단된다고 주장하지 않는다.
- 성공 응답의 model·answers·type·choice와 필요한 필드를 검증하고 choice가 정의한 키인지 확인한 후 매핑한다.
- 외부 장애를 랜덤 대사나 '다시 물어봐'라는 정상 AI 결과로 위장하지 않는다.
- 위험한 행동·건강 등 고위험 질문에 대한 안전한 안내·거절 정책을 구현 전에 정한다. '오락용' 문구만으로 안전 처리가 완료됐다고 간주하지 않는다.

- 시스템 한국어 sans-serif 스택을 우선 사용하고 본문 최소 14px, 본문 line-height 1.6. 커스텀 폰트 의존성은 만들지 않는다.
- 4px 간격 스케일, 둥근 형태, 안정적인 답변 영역 높이. 배경 움직임·무의미한 바운스·블러를 추가하지 않는다.
- 컴포넌트 구현 전에 DESIGN.md에 토큰·레이아웃·상태·접근성·모션 규칙을 작성한다. 현재 이 디자인은 미승인 제안이다.

### 확정된 Three.js 모델 방향과 구현 제안

#### 이미지에서 관측한 형태

- 왼쪽 위에 작은 끝이 있고 점차 부풀어 중앙 몸통으로 이어지는 나선 껍질.
- 오른쪽 아래로 길게 빠지는 뾰족한 끝과 비대칭 실루엣.
- 정면 오른쪽에 열린 큰 개구부와 두툼하게 말린 테두리.
- 개구부 안의 짙은 청록·검정 계열 격자 스피커.
- 오른쪽 위의 작은 보라색 돌출부와 밝은 아이보리·민트색 고리 손잡이.
- 연보라·푸른 음영·분홍빛 하이라이트의 둥글고 부드러운 장난감 질감.
- 참고 이미지에는 당겨진 줄과 후면이 보이지 않는다. 줄이 늘어나는 구조·후면 두께는 구현용 해석으로 분리한다.

#### 코드에서 직접 모델링

- Three.js를 직접 사용하고 TypeScript 타입 의존성을 함께 준비한다. React Three Fiber·Drei·CSG·외부 모델·3D 편집기 파이프라인은 기본 범위에서 제외한다.
- 커스텀 파라메트릭 메시로 크기가 변하는 나선 몸통과 길어진 끝을 만든다. 기본 도넛 여러 개를 쌓은 형태로 대체하지 않는다.
- 껍질 입구를 실제 열린 형태로 구성하고, 말린 입구 테두리·어두운 안쪽 면·스피커 판을 별도 구성한다. 불투명 몸통 위에 평면 그림만 붙여 개구부를 흉내 내지 않는다.
- 스피커는 실제 3D 판을 개구부 안에 넣고 격자 무늬는 절차적 텍스처로 표현하는 제안이다. 모든 구멍을 개별 메시로 만들지는 않는다.
- 손잡이·받침·줄을 독립된 그룹으로 두고 당기기 거리와 복귀를 조절한다.
- 기본 카메라는 참고 이미지에 가까운 3/4 정면 구도다. 자유 회전·줌은 첫 버전에서 제외하여 줄 조작과 충돌하지 않게 한다.
- 부드러운 조명과 재질·색 변화로 볼륨을 표현하되 반사·유리·과도한 금속 광택을 피한다. 참고 이미지의 모든 붓질까지 정확히 복제한다고 약속하지 않는다.

#### 당기기와 API 연결

- 고리 부근을 잡으면 줄이 늘어나고, 정해진 거리 이상 당긴 뒤 놓으면 질문을 한 번 전송한다.
- 짧게 당기기·pointer cancel은 호출하지 않고 원위치로 복귀한다.
- 버튼·키보드 실행도 동일한 질문 처리 경로를 사용한다. 시각적 3D 동작이 별도의 중복 API 요청을 만들지 않는다.
- API 대기 상태, 성공 답변, 오류를 구분하고 긴 대기 동안 끝없는 반복 모션을 하지 않는다.

#### Next.js·성능·대체 표현

- WebGL은 클라이언트 경계 안에서만 초기화하고 Three.js는 지연 로드한다. 질문·로그인 UI는 Canvas 준비 여부와 무관하게 사용할 수 있게 한다.
- Canvas 준비·실패·컨텍스트 손실을 처리한다. 대체 표현과 3D를 동시에 겹쳐 표시하지 않는다.
- WebGL 미지원·초기화 실패 시 같은 형태의 자체 정적 SVG와 실제 실행 버튼을 제공한다. 이는 3D 구현과 별개의 대체 표현임을 명시한다.
- reduced-motion에서는 정적인 3D 표시와 최소 상태 변화만 사용한다. 입력 기능은 유지한다.
- 화면 크기에 맞춰 카메라·모델 크기를 조정하고 당기는 고리까지 포함한 최대 모션 범위를 확보한다.
- 모바일 픽셀 비율·메시 분할·그림자를 제한하고 기본 상태에서는 필요한 때만 렌더한다. 숨겨진 탭·언마운트 시 모션을 중지한다.
- geometry·material·texture·renderer와 이벤트 리스너·애니메이션을 정리한다. 개발 재마운트·페이지 이동에서 Canvas와 핸들러가 중복되지 않게 한다.
- 첫 소규모 모델 확인에서 실루엣·개구부·격자·고리의 인식 가능성을 먼저 검증하고, 실제 장면의 성능을 측정한 뒤 디테일을 조절한다.

### 입력·접근성

- 마우스·터치는 포인터 기반 당기기와 복귀 애니메이션. 문턱 미달·pointer cancel은 API 호출 없이 복귀한다.
- 키보드·스크린리더는 실제 버튼으로 동일 액션을 실행한다. 장식 그림만 클릭 가능하게 만들지 않는다.
- focus-visible, label, 오류와 입력 연결, 결과 live region, loading 상태 제공.
- prefers-reduced-motion에서는 당기기·쉘 움직임을 최소화하되 같은 기능을 제공한다.
- 일반 데스크톱은 가능한 한 한 화면에 들어오게 한다. 짧은 화면·모바일 키보드·긴 오류는 스크롤을 허용하고 조작부를 자르지 않는다.
- 375px / 768px / 1440px 폭과 짧은 높이, 한국어 긴 입력으로 확인한다.

## 10. 서버리스 저장소와 운영

- 공용 Redis에 버전 prefix로 OAuth 거래, 세션, 요청 결과, 사용자 제한·공용 예산·동시 슬롯을 분리한다.
- 세션은 고정 1시간, OAuth 거래는 최대 5분, 중복 응답·모호한 요청은 5분을 초기 TTL 제안으로 둔다.
- 처리 완료 결과는 답변과 질문 해시만 단기 보관한다. 질문 원문은 저장하지 않는다.
- 슬롯 확보·counter·결과 처리 중 상태는 원자적 연산으로 구현한다. GET 후 SET만으로 경쟁을 제어하지 않는다.
- 함수 강제 종료 시 슬롯 복구를 위한 lease TTL을 두되, provider가 실제 처리를 계속할 가능성까지 고려한다. 외부 호출 종료·취소가 보장된다고 가정하지 않는다. Redis 슬롯만으로 모든 상황의 upstream 동시성을 완벽히 보증한다고 주장하지 않는다.
- provider 타임아웃은 배포 함수 예산보다 짧게 설정하고 실제 배포 제한을 확인한다. 첫 제안은 upstream 10초이며 지연 시험 후 조정한다.
- 로그: 요청 식별자, 정제된 상태 코드·오류 분류, 지연, 개인정보 없는 사용량만 허용. 키·쿠키·토큰·인증 코드·질문 원문·프로필 원문 금지.
- 환경값 이름 제안: APP_ORIGIN, DATAGSM_CLIENT_ID, DATAGSM_REDIRECT_URI, JEB_API_KEY, 선택한 Redis 연결값. 실제 비밀 파일은 열거나 수정하지 않는다. .env.example에는 placeholder와 설명만 추가한다.
- preview와 production의 redirect URI·쿠키·Redis namespace를 분리한다. 임의 preview 도메인을 자동으로 callback 허용하지 않는다.

### 저장소 도입 순서와 되돌리기

1. Expand: 빈 버전 namespace와 설정·연결 검증을 준비한다. 운영 트래픽은 받지 않는다.
2. Backfill: 신규 앱의 임시 데이터라 기존 데이터 이전 없음.
3. Switch: 검증된 로그인·질문 경로를 배포한다. 롤백은 이전 앱 버전으로 되돌려 신규 로그인·질문을 닫는다.
4. Contract: 기존 저장소·공개 API 삭제 없음. 변경 때는 새 prefix를 추가하고 기존 세션 TTL이 지난 뒤에만 만료된 prefix를 정리한다. 첫 버전에서 파괴적인 데이터 제거 작업 없음.

Redis 사용 자체는 사용자 확정 사항이다. 공유 저장소 공급자, 비용, 연결 클라이언트는 아직 확정하지 않았다. 선정 후 공식 문서와 실제 원자적 연산 지원을 확인한다. 외부 서비스 생성·비용 발생은 별도 승인받는다.

## 11. 구현 순서와 단계별 완료 기준

### 1단계 — 기반 계약·테스트·디자인

- API 타입·오류 코드·답변 목록·자격 정책·설정 검증·저장소 경계를 정의한다.
- DESIGN.md와 테스트 도구 설정을 추가한다. 개발 의존성은 Vitest와 Playwright를 제안하되 도입 전 승인한다.
- 참고 이미지를 DESIGN.md에 기록하고 Three.js 모델의 실루엣·개구부·스피커·고리 구조를 작은 렌더링으로 먼저 확인한다. 부품·표면 오류를 확인한 뒤 상세 UI를 진행한다.
- 자격 분기, 입력 검증, Jeb 200·401·422 파싱 테스트를 먼저 실패 상태로 만든다.
- 완료: 실제 타입 검사·단위 테스트로 계약을 확인하고 FSD 경계를 통과한다. 이 단계의 모의 응답은 제공된 샘플 기반 테스트 fixture라고 명시한다.

### 2단계 — DataGSM 로그인 세로 기능

- 거래 생성·콜백·사용자 조회·자격 검사·세션·로그아웃을 연결한다.
- state 누락·불일치·재사용·만료, 미승인 선생님, null 대상, 졸업·자퇴 상태를 테스트한다.
- 실제 등록된 client와 callback으로 허용된 학생 계정 로그인·새로고침·로그아웃·보호 API 거부를 확인한다.
- 선생님 실제 테스트 계정이 없다면 mock 자격 테스트와 실제 학생 로그인을 분리 보고하고 선생님 실연동은 미검증으로 남긴다.
- 완료: 인증하지 않은 직접 API 요청이 Jeb을 호출하지 않고, 세션 폐기 후 같은 쿠키를 재사용해도 거부된다.

### 3단계 — Jeb 질문 세로 기능

- 서버 질문 경로, 고정 대사 매핑, mutation, 한도·중복·동시성·타임아웃을 구현한다.
- 실제 키로 최소 호출하여 choice → 대사 표시를 확인한다. 개인 정보는 보내지 않는다.
- 잘못된 choice·깨진 JSON·upstream 401/422/429/5xx·타임아웃·Redis 장애를 테스트한다. 미관측 오류 fixture는 모의라고 명시한다.
- 완료: 실호출 결과가 올바르게 표시되고, 불허·중복·빈 입력은 외부 호출 전에 거부되며 장애를 정상 대사로 위장하지 않는다.

### 4단계 — 소라고동 화면·당기기

- 승인된 디자인으로 로그인·플레이 화면과 직접 제작한 Three.js 모델을 완성하고 연결한다.
- drag threshold·cancel·키보드 대체, loading·결과·error·만료·reduced-motion을 연결한다.
- 실제 3D 장면의 당기기 전·중·후 프레임을 같은 구도에서 캡처하여 고리 이동·줄 길이·복귀·모델 잘림을 확인한다.
- 완료: 포인터와 키보드에서 한 액션이 한 요청으로 연결되고 재당기기로 중복 호출하지 않는다. 긴 한국어와 짧은 화면에서 조작부가 잘리지 않는다.

### 5단계 — 통합 검증·배포 준비

- 단위·통합·브라우저 테스트와 저장소 제어 경쟁 조건 테스트를 실행한다.
- 실제 UI를 375/768/1440px와 짧은 화면으로 캡처하고 대비·포커스·오버플로를 확인한다.
- 모든 프로젝트 검사를 실행하고 최소 실제 로그인 → 질문 → 새로고침 → 로그아웃 경로를 확인한다.
- 배포는 별도 허가 후 진행한다. 고정 도메인의 DataGSM callback·Redis·Jeb 환경값을 설정하고 배포된 주소에서 동일 흐름을 읽어 확인한다.
- 완료: 실제 실행 결과를 기록한다. credential·provider 설정이 없으면 로컬 fixture 테스트 통과와 실연동 미검증을 분리하고 출시 완료로 주장하지 않는다.

## 12. 검증 계획

### 자동 테스트

- 사용자 유형·계정 상태·학생 역할·null 필드에 대한 자격 allow/deny.
- PKCE 생성·OAuth 거래 일회성·state 불일치·외부 redirect 차단.
- 세션 생성·쿠키 옵션·만료·로그아웃 및 직접 API 인증 우회 차단.
- Jeb 성공·두 오류 형식·알 수 없는 choice·비JSON·타임아웃.
- 동일 요청 ID·다른 질문 충돌·공유 counter·슬롯 해제·장애 시 fail closed.
- CSRF Origin 검증, 질문 길이·body 형식, 원문·비밀 로그 비노출.
- 브라우저 상태 전이·중복 클릭·키보드·터치·pointer cancel·reduced-motion.
- 3D geometry의 유한 좌표·노멀·바운딩, 장면 준비·재마운트·정리, WebGL 실패·컨텍스트 손실·대체 표현 전환.
- 실제 렌더 후 참고 이미지와 나선 실루엣·개구부·스피커·손잡이를 비교하고, 375/768/1440px의 당기기 최대 프레임에서 잘림·이중 실루엣·부품 관통을 확인한다.

### 기존 검사

```sh
pnpm peers check
pnpm lint
pnpm lint:fsd
pnpm format:check
API_BASE_URL=http://localhost:8080 pnpm check-types
API_BASE_URL=http://localhost:8080 pnpm build
```

신규 테스트 명령은 도구 도입 때 package.json과 CI에 함께 추가한다. 현재 존재하지 않는 test 명령을 이미 실행할 수 있다고 주장하지 않는다. 기존 Hermes 포팅 테스트도 유지한다. 계획 단계에서는 위 검사·제품 실행을 수행하지 않았다.

## 14. 승인 전에 정할 사항

재학생·승인 완료 선생님 허용, 고정 1시간 세션, Redis 사용, 참고 이미지 기반 Three.js 직접 모델링은 사용자 확정 사항이다.

1. Redis 공급자·비용·연결 클라이언트와 테스트 개발 의존성을 선정·승인할지.
2. 시각 방향과 답변 후보, 초기 개인·공용 제한값을 승인할지.
3. Jeb 제공자에게 선생님 포함 서비스 사용이 허용되는지 확인할 담당자.

요구 선택은 완료됐지만 기술 제안·전체 계획은 아직 미승인이다. 구현 착수와 배포는 자동으로 진행하지 않는다.
